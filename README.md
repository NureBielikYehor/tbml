# StepFund

`tbml` — технічна назва репозиторію за назвою дисципліни; бренд платформи — **StepFund**.

Краудфандинг із прогнозом успішності та поетапною виплатою коштів після голосування вкладників. Тема №18 з дисципліни «Технологія блокчейн та машинне навчання».

Команда: **Бєлік Єгор і Глоба Максим, ПЗПІ-23-6**. Працюємо спільно над усіма частинами. Репозиторій: [NureBielikYehor/tbml](https://github.com/NureBielikYehor/tbml).

Для виконання ЛР2 використовуйте [розділ блокчейн-частини](#блокчейн-частина-лр2). Він містить самостійний запуск контрактів із заглушкою оракула. ML, API та вебінтерфейс — основа для наступної ЛР3, де їх вимагає методичка.

## Реалізовано

- Три типи Solidity-контрактів: фабрика, кампанія з етапами/голосуванням/поверненням, реєстр прогнозів і моделей.
- Реальний Python ML: частка успіху в категорії як baseline, LogisticRegression і HistGradientBoosting із числовими ознаками та справжніми короткими описами.
- Node/Express oracle: незмінні входи → inference → аудит → транзакція дозволеної адреси.
- Український інтерфейс: створення, прогноз, внески, звіти, голосування, транші й повернення.
- Виконаний Jupyter EDA з 8 графіками, порівняння/абляції/калібрування ML, контрактні та Python-тести, наскрізна демонстрація.

Вебзастосунок — **локальний навчальний демонстратор** на chainId 31337. Він використовує розблоковані тестові акаунти Hardhat. Зовнішнє розгортання, приватні гаманці користувачів, IPFS і фінальний оформлений звіт не є частиною цього запуску.

## Швидкий запуск у підготовленому workspace

```bash
npm run dev
```

Відкрити **http://127.0.0.1:3000**. Команда компілює контракти, запускає нову локальну мережу, деплоїть factory/registry та запускає API з Python worker. Порти 3000 і 8545 мають бути вільними. Для зупинки — Ctrl+C. Перезапуск створює новий in-memory blockchain, тому кампанії попереднього запуску в новій мережі відсутні.

У правому верхньому куті можна перемикати навчальні ролі: автор, вкладник A, вкладник B, адміністратор. Для голосування є кнопка пришвидшення часу **лише в локальному демо**. Кошти справжньої мережі не використовуються.

## Відтворення з нового клону

Потрібні Node.js 24+, Python 3.11+ (перевірено на 3.12), мережа для початкового завантаження залежностей/даних. Використовуйте наявний Python відповідної версії замість `python3.12`, якщо він має іншу команду.

```bash
npm ci
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python scripts/download_kickstarter.py
.venv/bin/python scripts/download_descriptions.py
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 .venv/bin/python -m ml.train
.venv/bin/python scripts/audit_kickstarter.py
.venv/bin/python scripts/create_eda.py
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 .venv/bin/python -m ml.experiments
npm run dev
```

Команди отримання даних призначені для нового клону; якщо CSV вже є, повторне завантаження пропустіть. На Windows синтаксис шляху Python і змінних середовища відрізняється. Встановлені залежності, сирі дані, модельні файли й локальний стан виключені з Git.

Параметри за замовчуванням працюють без `.env`. Для зміни порту/інтерпретатора скопіюйте `.env.example` у `.env`. Адреси контрактів генеруються під час деплою в `data/local/deployment.json`.

## Перевірки і сценарій захисту

```bash
npm test
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
```

Коли `npm run dev` працює, в іншому терміналі:

```bash
npm run test:integration
npm run demo
```

`demo` реально створює кампанію, отримує прогноз через API/оракул, збирає 10 ETH від двох тестових адрес, схвалює та виплачує перший транш 4 ETH, відхиляє другий етап і перевіряє повернення **3.6 та 2.4 ETH**, залишок контракту **0**. Хеші транзакцій, gas і локальний час підтвердження записуються в `reports/blockchain/demo.json`.

Інтеграційні тести створюють окремі тестові чернетки й перевіряють відхилення чужого Origin, некоректних запитів, підміненого контенту та невідповідних параметрів. Запускайте їх у власній локальній навчальній мережі.

Для роздільного запуску доступні `npm run chain`, `npm run deploy`, `npm start`.

## Перевірені результати ML

Основний CSV має 378661 кампанію; після вибору successful/failed — 331675. Описи приєднано за ID для 165434 із них. Усі три методи порівнюються на цій самій підмножині: train 113038, validation 23069, test 24845; 4482 записи на часових межах вилучено, щоб не навчатися на ще невідомих результатах.

| Метод | F1 test | ROC-AUC test | Brier test |
|---|---:|---:|---:|
| Частка успіху в категорії | 0.7302 | 0.7297 | 0.2213 |
| LogisticRegression | **0.7631** | **0.8049** | **0.1912** |
| Histogram gradient boosting | 0.7542 | 0.7917 | 0.1978 |

Модель обрана за validation ROC-AUC. Значення зберігаються в `reports/ml/metrics.json`; абляції й умовний bootstrap — в `reports/ml/experiments.json`. Після нового навчання результати потрібно перевірити заново. Поле `pr_auc` у JSON означає average precision (AP), обчислену `average_precision_score`, а не трапеційну площу під PR-кривою.

**Обмеження даних:** Web Robots надає короткий `blurb`, а не повну історію. Snapshot не доводить незмінності тексту з моменту запуску; покриття класів нерівномірне, явна ліцензія повторного використання знімка не знайдена. Сирі тексти не публікуємо в Git. Модель дає ретроспективний прогноз збору на Kickstarter, не гарантію виконання й не перевірену точність для нових криптокампаній. Бюджет у фіатній валюті для ML задається окремо від тестового ETH, без автоматичного курсу.

## Блокчейн-частина ЛР2

ЛР2 запускається скриптами без інтерфейсу та ML. Контракти мають глобальну аварійну зупинку, атомарну ротацію оракула, NatSpec і перевірки ролей/станів. Метадані й звіти зберігаються в SQLite (`data/local/content.sqlite3`), у ланцюгу — їхні хеші. Під час читання хеш перевіряється. Наявні JSON-файли попереднього демо імпортуються після перевірки цілісності.

Підготовка інструментів на Linux x86_64 (Foundry 1.9.0, native solc 0.8.38, перевірка upstream SHA-256):

```bash
npm ci
npm run tools:blockchain
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-security.lock
```

Локальні перевірки:

```bash
npm test
npm run test:contracts
npm run coverage:contracts
npm run security
npm run lab2:demo
npm run lab2:integrity
npm run lab2:gas
npm run lab2:optimize
```

`lab2:demo`, `lab2:integrity`, `lab2:gas` і `lab2:optimize` створюють окрему тимчасову локальну мережу. Вебсервер, Python-модель і вільний порт 8545 для них не потрібні. `lab2:demo` використовує явно позначену заглушку з оцінкою 7200/10000; це тестове значення, а не прогноз ML.

Для окремого deploy/seed/oracle запустіть `npm run chain`, а в іншому терміналі — `npm run lab2:deploy`, `npm run lab2:seed`, `npm run lab2:oracle`, `npm run lab2:demo -- --deployed`. Ці команди використовують `data/local/lab2-31337.json`, окремо від стану вебдемонстратора.

Foundry перевіряє контракти, події, власні помилки, час, повторні виклики, шкідливих одержувачів і крайні суми. Фазинг виконує 256 наборів входів; 3 інваріанти — 128 послідовностей по 64 виклики. Solidity-покриття вимірюється `forge coverage --ir-minimum` для власних контрактів; поріг рядків і гілок — 85%. Мінімальна IR-оптимізація може залишати попередження про прив'язку окремих вихідних рядків; повний вивід зберігається. Це вимір інструмента, а не доказ відсутності помилок.

Slither аналізує всі три контракти через імпорти фабрики. `scripts/security.py` зберігає кожне зауваження з поясненням і завершується помилкою для нових нерозібраних зауважень. GitHub Actions налаштовано на запуск тестів, покриття, аналізатора, сценарію та перевірки файлу на push/PR. Після виконання workflow результати доступні як його артефакт.

Для максимальної оцінки обрано два додаткові завдання — фазинг із трьома інваріантами та автоматичні перевірки. Фазинг й інваріанти перевірені локально. Перший запуск GitHub Actions для змін ЛР2 ще потрібно підтвердити після їх публікації в репозиторії.

Газ вимірюється для всіх функцій ABI, що змінюють стан, і для розгортання. Дві оптимізації порівнюються на однаковому EVM-знімку: ущільнення структури етапу, потім бітова мапа голосів. Вартість основного сценарію не включає спільне розгортання фабрики/реєстру. Для графіків і обчислення USD встановіть також `requirements.lock`, після чого:

```bash
npm run lab2:charts
```

Курс ETH/USD отримується з публічного Coinbase API разом із часом запиту; 5 і 50 gwei — явно задані звичайний та підвищений сценарії. Для автономного розрахунку можна задати `ETH_USD=... npm run lab2:charts`; тоді курс позначається як припущення.

Пауза блокує також виплати й повернення; адміністратор має зняти її для відновлення. Строки під час паузи продовжуються, тому після відновлення прострочений етап може перейти до повернень. Сума цілі обмежена uint128; кворум обчислюється у uint256. URI маніфесту обмежено 256 байтами. Власника змінюють у два кроки; відмову від ownership вимкнено, щоб не втратити можливість аварійного відновлення.

Ця кампанія вже завершила демонстраційний сценарій. Для нового проходження створіть нову кампанію через seed. Команда `lab2:audit:sepolia` повторно перевіряє кінцеві значення, підтвердження транзакцій, обидва етапи, хеші позаланцюгових даних і нульовий залишок. Фактичні Sepolia gas/fee збережені окремо від локальних вимірювань Hardhat; не підміняйте один набір чисел іншим.

1. Створіть окремі навчальні акаунти локально:

   ```bash
   npm run lab2:wallets -- --create
   ```

   Команда створить `.env.sepolia` з правами 0600 і виведе лише публічні адреси. Наявний файл не перезаписується. Ключі залишаються локально та ігноруються Git.

2. Отримайте тестовий Sepolia ETH через [крани з офіційного переліку Ethereum](https://ethereum.org/developers/docs/networks/#sepolia). Поповніть ADMIN для розгортання, ORACLE для прогнозу, AUTHOR для керування кампанією та обох BACKER для внесків/голосів/повернень. Демо збирає лише 0.002 тестового ETH; окремо потрібні кошти на газ. Справжній ETH купувати не потрібно.
   Якщо кран поповнює лише ADMIN, команда `lab2:fund:sepolia` доведе баланси інших навчальних адрес до 0.005 тестового ETH кожна. Для перегляду плану без переказів: `npm run lab2:fund:sepolia -- --dry-run`.

3. Відкрийте `.env.sepolia` локально. Вкажіть `SEPOLIA_RPC_URL` від RPC-провайдера та `ETHERSCAN_API_KEY` від [Etherscan](https://etherscan.io/myapikey). Приватні ключі й цей файл у чат не надсилайте.
4. Після поповнення й налаштування:

   ```bash
   npm run compile
   npm run lab2:fund:sepolia
   npm run lab2:deploy:sepolia
   npm run lab2:seed:sepolia
   npm run lab2:oracle:sepolia
   npm run lab2:demo:sepolia
   npm run lab2:verify
   npm run lab2:audit:sepolia
   ```

   Скрипти перевіряють chainId 11155111. Голосування в Sepolia триває 120 секунд: сценарій чекає реальні блоки, без перемотування часу. Повторний запуск сценарію продовжує вже створену кампанію; якщо вікно голосування пропущене, відсутні голоси не підробляються й очікуваний сценарій може завершитися помилкою. Для нового проходження створіть нову кампанію через seed.

5. Після нового розгортання збережіть фактичні адреси й посилання на верифікований код. Наведені вище адреси належать перевіреному запуску 11.11.2026; новий seed створить іншу кампанію.

Підготовлені стандартний JSON компіляції й ABI-аргументи конструктора використовуються для [Etherscan V2 verification](https://docs.etherscan.io/api-reference/endpoint/verifysourcecode). Суху перевірку пакета для локального демо можна виконати `node scripts/lab2-verify.mjs --local --prepare-only`; вона не надсилає запит до оглядача.
